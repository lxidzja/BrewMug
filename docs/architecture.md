# Архітектура BrewMug

## Огляд

```
                  ┌─────────────────────────────┐
   гість  ──────► │  статичний HTML/CSS (dist/) │  ← збірка Astro
                  └──────────────┬──────────────┘
                                 │ JS-поліпшення (≈3 КБ)
                                 ▼
                  ┌─────────────────────────────┐
                  │  /api/* (Cloudflare Pages)  │
                  └──────┬───────────────┬──────┘
                         ▼               ▼
                    D1 (SQLite)     Telegram / webhook
```

Сайт працює без бекенду: усі сторінки — статичні. Бекенд потрібен лише для двох форм і списку вільних годин.

## Шари

| Шар | Файли | Відповідальність |
|---|---|---|
| Контент | `src/data/**/*.yaml` | адреса, години, меню, тексти; єдине джерело |
| Перевірка даних | `scripts/load-data.mjs` | Zod-схеми + правила BR (15+ позицій, 4 категорії, наявність ілюстрацій) |
| Доменна логіка | `src/lib/hours.ts`, `booking.ts`, `validation.ts` | «відчинено зараз», слоти, нормалізація полів |
| Презентація | `src/pages/*`, `src/components/*` | сторінки й компоненти; стан відсутній (SSG) |
| Клієнтський JS | `src/scripts/*.ts` | прогресивне поліпшення: статус, форма, повідомлення |
| Сервер | `server/handlers.ts`, `store.ts`, `notify.ts` | валідація, місткість, зберігання, сповіщення |
| Платформа | `functions/api/*`, `server/dev.mjs` | тонкі обгортки: Cloudflare Pages / локальний Node |
| Дизайн-система | `design/tokens.mjs` → `src/styles/tokens.css` | кольори, типографіка, відступи |

## Чому так

- **Astro, а не SPA.** Вимога BR 007 і НФВ-1: контент без JavaScript. Статичні сторінки = нуль JS для читання меню й контактів.
- **YAML, а не БД для контенту.** BR 002: оновлення меню без розробника; зміни проходять рев'ю в Git-історії.
- **Сервер не залежить від платформи.** `server/handlers.ts` приймає звичайний `Request` і повертає `{status, body}`. Cloudflare-обгортка — 20 рядків. За потреби перенос на іншу платформу — заміна обгорток.
- **Абстракція сховища.** `Store` має три реалізації: D1 (production), пам'ять (тести), файл (локальна розробка).
- **Прогресивне поліпшення.** Форма надсилається й без JS; скрипт лише додає перевірку, вільні години та повідомлення без перезавантаження.

## Потік броньювання

1. Гість відкриває `/broniuvannia/` — сервер відрендерив слоти на поточну дату з YAML.
2. Зміна дати → `GET /api/availability` → перемальовування чіпів (зайняті = `disabled` + перекреслені).
3. Надсилання → `POST /api/booking`:
   - honeypot і мінімальний час заповнення → відсів ботів;
   - Zod-валідація (та сама схема, що в браузері);
   - перевірка горизонту, запасу часу, місткості;
   - запис у сховище;
   - сповіщення (помилка каналу не скасовує запис);
4. Відповідь: `201` + JSON (JS) або `303` на сторінку подяки (без JS).

## Гарантії

- **Немає втрати заявки через невдале сповіщення** — запис іде першим.
- **Немає переповнення залу** — перевірка суми гостей у слоті (`capacityPerSlot`). На D1 потрібне транзакційне або умовне вставлення для повної атомарності (див. нижче).
- **Немає публікації заглушок** — production-збірка падає на `placeholder: true`.

## Відоме обмеження

Місткість перевіряється в два кроки (читання → вставка). Під навантаженням двоє гостей теоретично можуть зайняти останні місця одночасно. Для кав'ярні з 24 місцями й кількома заявками на годину це прийнятно; для повної атомарності треба `INSERT ... SELECT WHERE (SELECT SUM(guests)...) + ? <= ?` в одному запиті D1 — винесено в беклог.

## Ліміт запитів

`rateLimit()` тримає лічильники в пам'яті процесу. На Cloudflare кожен ізолят має власний лічильник, тому це орієнтир, а не жорстка гарантія. Для строгого ліміту — Cloudflare Rate Limiting Rules або Durable Object (беклог).

## Розширення ілюстрацій

`design/build-illo.mjs` малює 25 SVG (чашки, склянки, десерти, снеки). Заміна на фото — компонент `Tile` приймає `src`, тому достатньо покласти файл у `public/illo/` під іншою назвою або змінити `illo` в YAML.
